Introduction

This report describes how the FoodBridge website was tested and what the results were. All tests were automated with Selenium WebDriver in Python and run in Google Chrome against the website running on my computer.

In total 140 test cases were written and run. The first 60 check every feature of the website. The other 80 add the features that were still missing and test the limits of every rule, for example the smallest and largest quantity a donor can post, or what happens after the fifth wrong reset code. All 140 test cases passed.

2

About FoodBridge

FoodBridge connects people who have extra food with people who can take it to those who need a meal. A restaurant, bakery or family posts the food they cannot use. A volunteer group or NGO claims only the servings it needs and picks the food up. The donor then confirms the pickup, and after that the claim is locked.

Donor

Post, edit and delete food. See who claimed it, with phone number, area, address and a map link. Confirm the pickup.

Collector

Search food by name, area or type. Claim part of a post. Release a claim before pickup. See the donor's location.

Admin

Answer forgot password requests with a 6 digit code. Add, edit, block or delete users, food posts and claims. Read the activity log.

Other features: a user can switch between donor and collector from the dashboard, the mobile number must be an 11 digit Bangladeshi number, and every user gives an area and address so both sides can find each other.

Test Approach

Every test case is a separate Python file in the selenium_tests folder, from tc001_signup_valid_donor.py to tc140_profile_dashboard_link.py. Each file can be run alone, and run_all_tests.py runs all of them in order and saves the results to test_results.csv.

Before each test case the demo data is reset, so every test starts from the same point and gives the same result no matter how many times it runs. Each test opens Chrome, does what a real user would do (typing, choosing from lists, clicking, confirming popups), then checks the message, the page or the data on screen. A screenshot of Chrome is saved after every test.

Two kinds of tests were used:

Functional tests

Check that each feature works with normal input and refuses wrong input, such as a missing name or a wrong password.

Boundary tests

Check the values right at the edge of each rule. For a rule like quantity 1 to 1000, the test tries 1 and 1000 (should be accepted) and 0 and 1001 (should be refused). Most mistakes in software happen at these edges.

Commands used:

cd selenium_tests
venv\Scripts\activate
python run_all_tests.py

Limitations

A few things were outside what these tests could cover:

Code expiry. A reset code stops working after 2 hours. This rule is in the server, but it was not tested automatically because the test would have to wait 2 hours and no page lets you set an older time.
One browser and screen size. All tests ran in Google Chrome on a laptop screen. Edge, Firefox, phones and tablets were not tested.
Other kinds of testing. Load and speed testing, security testing and testing the server routes directly without a browser were not part of this work.
9

Conclusion

FoodBridge was tested with 140 automated test cases covering sign up, login, profile, the donor and collector dashboards, partial claims, pickup confirmation, role switching, password reset through the admin, location, the admin panel, the home page and navigation. All 140 test cases passed.

The boundary tests show that every limit in the website works exactly at its edge: values just inside are accepted and values just outside are refused. Because every test resets the data first and lives in its own file, the whole set can be run again at any time to check that later changes have not broken anything.
